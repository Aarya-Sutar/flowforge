## 2. Why This Phase Exists

Every previous phase ran on `localhost`, reachable only by the person running it. This phase is about the specific, non-obvious translation work required to take a Docker Compose stack — which assumes one machine, one network, containers that can find each other by service name — and turn it into something that runs on infrastructure you don't own, is reachable by the public internet, and has to be secured, monitored, and paid for accordingly. None of the application code changes; everything here is about the environment around it.

## 4. Core Concepts (AWS Fundamentals, from zero)

### Cloud computing, region, and availability zone

"The cloud" is just someone else's computers, rented by the hour/second, reachable over the internet, managed through an API instead of a keyboard plugged into the machine. AWS runs data centers grouped into **regions** (`us-east-1` = Northern Virginia, an independent geographic area) — this project defaults to `us-east-1` (`variables.tf`). Within a region, AWS operates multiple **availability zones (AZs)** — physically separate data centers with independent power/networking, close enough for low-latency connections between them but far enough apart that one catching fire doesn't take out the other. `vpc.tf`'s `data "aws_availability_zones" "available"` looks up whichever AZs exist in the configured region and spreads subnets across (by default) 2 of them — this is what "highly available" means mechanically: if one AZ has a problem, resources in the other keep running.

### VPC, subnet, and the public/private distinction

A **VPC** (Virtual Private Cloud) is your own private, isolated slice of AWS's network — `vpc.tf`'s `aws_vpc.main`, given the address range `10.0.0.0/16` (about 65,000 possible addresses). A **subnet** is a smaller range carved out of that VPC, pinned to one specific AZ. The **public vs. private** distinction isn't a property of the subnet itself — it's determined entirely by its **route table**: `aws_route_table.public` (`vpc.tf`) routes `0.0.0.0/0` (anywhere) through the **Internet Gateway**, which is what makes a subnet "public." The private subnets get no such route — by default, traffic can only reach other things inside the same VPC. This is the literal mechanism behind "RDS and ElastiCache are private": they simply have no path to the internet at all, not even one blocked by a firewall.

### Security groups

A security group is a stateful firewall attached to a resource (not a subnet) — `security_groups.tf` defines four: one for the ALB (allows port 80 from anywhere), one for the ECS tasks (allows 8000/3000, but *only* from the ALB's security group — not from any IP range), one for RDS (5432, only from the ECS tasks' security group), one for Redis (6379, same pattern). "Stateful" means a rule allowing inbound traffic automatically allows the matching outbound response — you don't write two rules for one conversation. Chaining security groups by reference (`security_groups = [aws_security_group.alb.id]`) rather than by IP range is what makes this genuinely least-privilege: even if the VPC's IP layout changed entirely, these rules keep meaning exactly the same thing.

### IAM: users, roles, policies, least privilege

**IAM** (Identity and Access Management) controls *who* (or *what*) can do *what* in an AWS account. A **user** represents a human or a long-lived credential; a **role** is an identity something can *assume* temporarily — no long-lived password, just a trust relationship ("ECS tasks are allowed to become this role") plus a **policy** (a JSON document listing exactly which actions are allowed on which resources). `iam.tf` defines two roles deliberately, not one, because they represent genuinely different trust boundaries — see section 4's IAM subsection below for the full reasoning; the short version is that the ECS *agent* pulling your image and reading secrets is a fundamentally different trust level than *your application code* running inside that image, and collapsing them into one role would give your app permissions it never asked for and doesn't need. "Least privilege" is the principle that a role should be able to do exactly what it needs and nothing else — `aws_iam_role.ecs_task` in this project has **zero** attached policies, because FlowForge's application code makes zero direct AWS API calls today. Adding broad permissions "in case we need them later" is exactly the anti-pattern this principle exists to prevent.

### Load balancer

An **Application Load Balancer (ALB)** is a managed reverse proxy: it has one stable public address, receives all incoming traffic, and distributes it across whichever backend targets are currently healthy — the same conceptual job `docker-compose.yml`'s port mappings do for a single machine, but for a fleet of containers that can be added, removed, or replaced without the public address ever changing. `alb.tf`'s listener rule does **path-based routing**: requests to `/api/*` go to the backend target group, everything else to the frontend — one ALB serving two different services.

### Managed database and managed cache

**RDS** (Relational Database Service) and **ElastiCache** are AWS operating PostgreSQL/Redis *for* you — patching, backups, failover — in exchange for less low-level control than running your own container. `rds.tf`/`elasticache.tf` configure the smallest available instance sizes (`db.t4g.micro`, `cache.t4g.micro`) — intentionally, for cost (section 6), with the trade-offs (single-AZ, no read replica) called out directly in code comments.

### Container registry and container orchestration

**ECR** (Elastic Container Registry) is where built Docker images live in AWS, the same role Docker Hub plays for public images — `ecr.tf` creates one repo each for the backend and frontend images (the celery-worker shares the backend's image, exactly like `docker-compose.yml`). **Container orchestration** (ECS) is the system that actually runs containers from those images, keeps the right number running, replaces ones that die, and reports their health — the cloud equivalent of what `docker compose up` does interactively on one machine, except durable and automatic.

## 5. Mental Model

The entire translation this phase does can be summarized as: **docker-compose.yml's five services map to five AWS things, and every `depends_on`/network relationship in Compose becomes an explicit security group rule instead of implicit Docker-network trust.** Locally, any container can reach any other container on the same Docker network by default — security comes from what ports are exposed. On AWS, nothing can reach anything by default — security groups are opt-in allow-lists, which is the fundamental posture shift "the cloud" requires: assume nothing is reachable until you explicitly say so.

## 6. Docker to AWS — the actual pipeline

```
Local Docker image (docker-compose.yml build)
        │  docker build
        ▼
Tagged image (project:tag)
        │  docker push (after `aws ecr get-login-password` auth)
        ▼
ECR repository (ecr.tf) — versioned, scanned on push
        │  referenced by ARN/URI in a task definition
        ▼
ECS Task Definition (ecs.tf) — the "recipe": image, CPU/memory, env vars, secrets, port mappings, log config
        │  an ECS Service maintains N running copies of this
        ▼
ECS Task — a running container (or set of them, for multi-container tasks), on Fargate (no EC2 instance to manage)
        │  registered as a target
        ▼
ALB Target Group → Application Load Balancer → the internet
```

Each arrow is a genuinely separate step with its own failure modes — worth tracing deliberately rather than treating "deploy" as one atomic action.

## 7. ECS/Fargate in Depth

- **Cluster** (`aws_ecs_cluster.main`): a logical grouping of services/tasks — mostly a namespace and a place to view aggregate metrics; with Fargate, it does *not* correspond to any actual servers you manage.
- **Task definition**: a versioned blueprint — which image, how much CPU/memory, what environment variables and secrets, which log group. Every deploy that changes any of these creates a *new revision*; nothing is mutated in place.
- **Task**: one running instance of a task definition — the actual container(s).
- **Service**: keeps a *desired count* of tasks running, replacing any that crash or fail their health check, and (for the backend/frontend) registers/deregisters them with the ALB target group as they start/stop.
- **Fargate** specifically: AWS runs the underlying compute for you — no EC2 instances to patch, size, or manage; you specify CPU/memory per task (`backend_cpu`/`backend_memory` etc. in `variables.tf`) and pay for exactly that, per second, while the task runs.
- **Container networking**: `network_mode = "awsvpc"` (required for Fargate) gives every task its own network interface and, here, its own public IP (`assign_public_ip = true`) — reachability is still controlled entirely by security groups, not by the presence of a public IP.
- **Health checks**: the ALB target group's health check (`alb.tf`, hitting `/api/health` — the exact endpoint built in Phase 1) is what actually decides whether a task receives traffic; a task can be "running" and still receive zero traffic if it's failing this check.

## 8. Deployment Runbook

**Prerequisites** (none of which exist in this environment): an AWS account, AWS CLI configured with credentials that have permission to create the resources below, Terraform ≥ 1.5, Docker.

1. **Copy and fill in variables**: `cp terraform.tfvars.example terraform.tfvars` (gitignored — never commit real values).
2. **Provision the network, database, cache, ECR repos, IAM, and ALB first** — deliberately *without* the backend image set yet, since ECS services need something to reference but the images don't exist yet:
   ```bash
   cd infrastructure/aws/terraform
   terraform init
   terraform apply -target=aws_vpc.main -target=aws_ecr_repository.backend -target=aws_ecr_repository.frontend
   ```
3. **Build and push the backend/worker image** (one image, two ECS services — same as `docker-compose.yml`):
   ```bash
   aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin <account-id>.dkr.ecr.us-east-1.amazonaws.com
   docker build -t flowforge-backend ./backend
   docker tag flowforge-backend:latest <ecr_backend_repository_url>:latest
   docker push <ecr_backend_repository_url>:latest
   ```
4. **Apply everything except the frontend service**, to get the ALB's real DNS name:
   ```bash
   terraform apply -var="backend_image=<ecr_backend_repository_url>:latest"
   terraform output alb_dns_name
   ```
5. **Build the frontend image with the real backend URL baked in** — this is the step Phase 6 already flagged as a hard requirement: `NEXT_PUBLIC_API_URL` is compiled into the client bundle, not read at runtime.
   ```bash
   docker build --build-arg NEXT_PUBLIC_API_URL=http://<alb_dns_name> -t flowforge-frontend ./frontend
   docker tag flowforge-frontend:latest <ecr_frontend_repository_url>:latest
   docker push <ecr_frontend_repository_url>:latest
   ```
6. **Final apply**, now with both images:
   ```bash
   terraform apply -var="backend_image=<ecr_backend_repository_url>:latest" -var="frontend_image=<ecr_frontend_repository_url>:latest"
   ```
7. **Seed the database** (optional, same script as local): this needs a one-off way to run `python -m app.seed` against the RDS instance from inside the VPC — e.g. `aws ecs execute-command` against a running backend task, or a dedicated one-off Fargate task. Not automated here; a reasonable Phase-9-adjacent improvement.
8. **Verify**: `curl http://<alb_dns_name>/api/health` should return `{"status": "ok", "database": "up"}`; open `http://<alb_dns_name>` in a browser for the frontend.

**Rollback**: `terraform apply -var="backend_image=<previous-tag>"` (and/or frontend) re-deploys the prior image — this only works if the previous tag is still in ECR, which `ecr.tf`'s `IMMUTABLE` tag setting guarantees (a tag can never be silently overwritten to point elsewhere).

**Tearing everything down** (to stop paying for it): `terraform destroy` — removes every resource this configuration created, in dependency order.

## 9. Cost Awareness

Approximate US-East-1 on-demand monthly costs at the sizes configured, for a lightly-used demo (not under real load — this is not a promise, it's an order-of-magnitude estimate to reason about, matching what the spec asks for):

| Resource | Approx. monthly cost | Why it costs what it costs |
|---|---|---|
| ALB | ~$16 base + ~$0.008/LCU-hour | Billed for existing, regardless of traffic, plus a usage component |
| Fargate (3 services × 0.25 vCPU/0.5GB, always on) | ~$25–30 total | Billed per-second while running; this is the single biggest controllable cost — `desired_count` directly multiplies it |
| RDS `db.t4g.micro`, single-AZ | ~$12–13 | Roughly doubles with `multi_az = true` |
| ElastiCache `cache.t4g.micro` | ~$10–12 | Roughly doubles with a replica added |
| NAT Gateway | **$0 — deliberately not provisioned** | The single biggest avoided cost in this design; see below |
| Data transfer, CloudWatch Logs storage | Usually a few dollars at this scale | Grows with traffic/log volume |

**Approximate total: ~$65–75/month**, dominated by the ALB and Fargate — both charge for existing/running regardless of real traffic, which is the central lesson of cloud cost awareness: **cost here comes from things running continuously, not from requests served.** A `docker compose up` on a free laptop has zero marginal cost for existing; an ALB and three always-on Fargate tasks do not.

**The NAT Gateway decision, explicitly**: a standard "ECS tasks in private subnets" architecture needs a NAT Gateway (~$32/month fixed, plus per-GB data processing charges) so those tasks can reach ECR/the internet without being directly internet-routable. This project instead puts Fargate tasks in **public** subnets with public IPs, relying entirely on security groups (section 4) to keep them unreachable except through the ALB. This is a real, load-bearing trade-off: it saves the single largest fixed cost in the whole architecture, at the cost of tasks technically having a public IP (mitigated, not eliminated, by the security group being the actual enforcement point) — worth naming plainly rather than glossing over.

**Never leave this running unintentionally**: `terraform destroy` when not actively demonstrating the deployment. Nothing in this repository automates tearing infrastructure down — that's a deliberate manual step, since automating destruction is exactly the kind of irreversible action that shouldn't happen without a human directly choosing it.

## 10. Cloud Failure Scenarios

Documented, not live-tested (no AWS access) — each follows the same WHAT → DETECTED HOW → RECOVERY → what's still a gap format used throughout this project's other failure-scenario sections:

| Scenario | Detected by | Recovery | Open gap |
|---|---|---|---|
| A backend Fargate task crashes | ALB health check fails (`/api/health` stops responding) | ECS service notices the task is no longer `RUNNING`/healthy and starts a replacement automatically — this is the entire point of `desired_count` + a service | Brief capacity reduction until the replacement passes its health check |
| RDS becomes briefly unreachable | Backend's own `/api/health` (Phase 1) reports `database: down`, `503` | RDS handles most transient issues transparently; a genuine AZ failure with `multi_az=false` (as configured here) means real downtime until AWS recovers the instance, since there's no standby to fail over to | This project's RDS is explicitly single-AZ (cost trade-off, section 9) — a real production deployment should flip `multi_az = true` |
| ElastiCache becomes unreachable | Same mechanism, and same open gap, as Phase 7's local Redis-outage investigation — nothing about moving to AWS changes that code path's behavior | Same — the ~105s slow-fail issue from Phase 7 is infrastructure-agnostic; it would reproduce identically here | Genuinely unresolved, same as Phase 7 |
| Wrong/missing environment variable in a task definition | The container fails to start or fails its health check immediately; ECS keeps cycling through failed starts | Fix the task definition (`ecs.tf` or the `-var` at apply time) and re-apply | None specific to AWS — same class of bug as a local `.env` misconfiguration |
| ECS can't pull the image ("permission denied" / "not found") | Task stuck in `PROVISIONING`/`PENDING`, then fails | Usually an execution role permission issue or a wrong image URI/tag | The execution role's managed policy (`iam.tf`) covers standard ECR pull permissions — a custom, more restrictive policy could break this if misconfigured |
| Health check misconfigured (wrong path/port) | Task technically running, ALB never marks it healthy, zero traffic ever reaches it | Exactly the class of bug Phase 7 found and fixed for the frontend's Docker healthcheck (`HOSTNAME=0.0.0.0`) — the same category of "looks broken, isn't" or "looks fine, is broken" mismatch, just at the ALB layer instead of Docker's | N/A — flagged here specifically because Phase 7's experience is directly relevant evidence for how to debug this exact class of AWS problem |

## 11. Trade-offs

- **Single-AZ RDS and ElastiCache** — real production would use Multi-AZ RDS and an ElastiCache replication group, roughly doubling those two costs, in exchange for automatic failover instead of downtime during an AZ-level failure.
- **No HTTPS** — the ALB listens on HTTP only. Real HTTPS needs a registered domain name and an ACM certificate, neither of which exists for this project; adding it would mean: register/point a domain, request an ACM cert, add an HTTPS listener referencing it, redirect HTTP→HTTPS. Deliberately not built for a domain-less demo.
- **No auto-scaling** — `desired_count` is a fixed number per service, not driven by CPU/request metrics. Reasonable for a portfolio-scale deployment; a real production setup would add `aws_appautoscaling_target`/`policy` resources keyed off ALB request count or CPU utilization.
- **Database migrations run inline in the backend container's startup command**, same as `docker-compose.yml` — fine at `backend_desired_count = 1`, a real race risk if scaled to multiple replicas simultaneously starting. Flagged directly in `ecs.tf`'s comments, not hidden.
- **No automated image build/push pipeline yet** — that's explicitly Phase 9's job (GitHub Actions); this phase's runbook is deliberately manual, matching the spec's own phase boundary.

## 12. Debugging Guide (for when this is actually deployed)

1. **"terraform apply fails."** Read the actual error — Terraform's error messages name the exact resource and API failure; resist the urge to guess before reading it fully (the same discipline Phase 7's live debugging required).
2. **"A task keeps restarting."** `aws ecs describe-tasks` for the `stoppedReason`; check the matching CloudWatch log group (`cloudwatch.tf` — one per service) for the container's own stdout right before it stopped.
3. **"The ALB reports every target unhealthy."** Check the health check path/port in `alb.tf` against what the container actually serves — and check the security group actually allows the ALB to reach that port (a very easy one-line SG mistake to make).
4. **"I can't connect to RDS/Redis from my own machine to debug."** By design — they're not internet-reachable (section 4). Use `aws ecs execute-command` to get a shell inside a running task (which *can* reach them, being in the same VPC/security-group graph) instead of trying to reach them directly.

## 17. Common Misconceptions

- **"Private subnet = secure."** A private subnet only removes the internet *route* — it says nothing about what else inside the VPC can reach that resource. The security group is what actually enforces "only the app can reach the database," not the subnet's routing table.
- **"Fargate means there are no servers."** There's no server *for you to manage* — AWS still runs your container on real hardware, and you still pay for the CPU/memory you reserve, whether or not it's fully used.
- **"Terraform validate proves the infrastructure would work if deployed."** It proves the configuration is internally consistent and syntactically correct — it cannot catch a wrong IAM permission, a real quota limit, or a genuine AWS-side outage. `terraform plan` against a real account (not done here) is a stronger, but still not complete, check.
